# 06. 구현 단계와 결정 기록

> **Status:** Working plan
> **Last reviewed:** 2026-07-30

## 먼저 한 가지 흐름을 끝까지 검증한다

테스트넷의 첫 목표는 기능을 많이 늘리는 것이 아니라, 한 캠페인이 시작부터 보상 수령까지 끊기지 않는지 확인하는 것이다. 아래 흐름이 안정적으로 작동해야 이후의 자동화와 어트리뷰션을 논의할 수 있다.

```mermaid
flowchart LR
    A["캠페인 설정\n예산 예치"] --> B["캠페인 조회\n인텔리전스 맥락 확인"]
    B --> C["퀘스트 수행\n완료 요청"]
    C --> D["운영팀 검증\n필요 시 채널 매핑 대조"]
    D --> E["GIWA에서\n보상 클레임"]
    E --> F["참여 이력\n확인"]

    classDef step fill:#e7f4ef,stroke:#25795d,color:#153d2e;
    class A,B,C,D,E,F step;
```

| 검증 항목 | 확인 방법 | 문제가 생기면 먼저 볼 곳 |
|---|---|---|
| 네트워크 전환 | 지갑에서 GIWA Sepolia 추가·전환 | chain ID, RPC, 지갑 호환성 |
| 예산 예치 | 캠페인 생성 트랜잭션과 상태 확인 | 토큰 승인, ETH/ERC-20 처리, 기간 |
| 완료 처리 | 같은 유저·퀘스트의 중복 처리 시도 | 권한, completion key, nonce |
| 보상 클레임 | 올바른 유저·잘못된 유저·재클레임 시도 | 완료 상태, 예산, 재진입 방지 |
| 참여 이력 | 완료 후 유저 상태 조회 | escrow 권한, mint/update 호출 |
| 채널 매핑 | 동일·유사 채널 신청, 지갑 변경 요청 검토 | 레지스트리, 대조 근거, 재확인 절차 |
| 종료 처리 | 종료 전·후 잔여 예산 회수 시도 | 종료 시각, active 상태, 프로젝트 권한 |

## 작업 순서

### Phase A — 이름과 인터페이스를 맞춘다

구현 전에 문서와 코드가 서로 다른 것을 말하지 않게 한다. 컨트랙트 이름을 `BaroCampaignEscrow`와 하나의 SBT 이름으로 통일하고, 완료 권한 모델을 운영자 직접 기록 또는 EIP-712 서명 방식 중 하나로 결정한다. 레퓨테이션 레벨의 입력값·조건·혜택도 한 번에 고정한다.

**완료 기준:** 문서와 실제 코드의 인터페이스가 충돌하지 않고, 테스트넷에서 어떤 흐름을 데모할지 한 장으로 설명할 수 있다.

### Phase B — 닫힌 테스트넷 루프를 만든다

캠페인 생성, 예산 예치, 퀘스트 완료 확인, 보상 클레임, 참여 이력 조회를 테스트넷에서 한 번에 확인한다. 운영팀은 예외 처리와 채널 매핑 대조 기록도 이 단계에서 함께 시험한다.

**완료 기준:** 정상 경로뿐 아니라 중복 클레임, 잘못된 네트워크, 예산 부족, 완료 권한 오류, 채널 매핑 불일치 같은 실패 경로도 재현할 수 있다.

### Phase C — 제한된 사용자 파일럿을 운영한다

테스트넷 흐름이 안정화된 뒤 소수의 프로젝트·채널·유저로 운영 절차와 UX를 검증한다. 이 단계의 목적은 큰 숫자를 만드는 것이 아니라, Baro Intelligence의 맥락이 실제 참여에 도움이 되는지와 운영팀의 수동 처리 비용이 어디에 쌓이는지를 확인하는 것이다.

| 볼 지표 | 확인하려는 질문 |
|---|---|
| 검증된 커뮤니티 참여 건수 | 관심이 실제 완료·보상으로 이어졌는가 |
| 발견 → 참여 전환율 | 인텔리전스 맥락이 행동을 돕는가 |
| 재참여율 | 보상이 끝난 뒤에도 경험이 반복되는가 |
| 온보딩 프로젝트·인증 채널 수 | 루프를 운영할 공급·유입 경로가 있는가 |
| 운영팀 수동 처리 시간 | 자동화가 필요한 병목은 어디인가 |
| 채널 매핑 보류·반려 비율 | 레지스트리·대조 절차를 보완해야 하는가 |

### Phase D — 자동화와 어트리뷰션을 넓힌다

파일럿에서 오류·운영 비용·어뷰징 패턴을 확인한 뒤에만 자동 검증과 고유 링크 추적을 확장한다. 기능을 먼저 많이 추가하는 것보다, 보상이 잘못 지급되는 경우와 잘못된 채널 매핑을 먼저 줄이는 것이 우선이다.

## 결정을 남기는 형식

새로운 아키텍처 결정을 할 때는 PR 또는 이 문서 하단에 아래 형식으로 남긴다. 실제 선택의 배경을 적어 두면, 나중에 코드와 정책이 달라졌을 때 왜 바꿨는지 추적하기 쉬워진다.

```markdown
### ARC-00X — 제목

- **Date:** YYYY-MM-DD
- **Status:** Proposed | Accepted | Superseded
- **Context:** 어떤 문제가 있었는가
- **Decision:** 무엇을 선택했는가
- **Consequences:** 얻는 것과 감수하는 것
- **Evidence:** PR, 커밋, 테스트 또는 배포 링크
```
